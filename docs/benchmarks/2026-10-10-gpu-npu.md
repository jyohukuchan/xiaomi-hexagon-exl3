# Adreno 750 versus Hexagon v75: matched backend benchmarks

Date: 2026-10-10 (Asia/Tokyo). Xiaomi 14 Ultra / SM8650, stock non-root
Android 16. This is an isolated benchmark, not a change to model inference.
The phone-hosted API stayed stopped and the model/runtime files were unchanged.

## What is being compared

Both devices use the same unmodified upstream llama.cpp build at
`a11f57ba93797579a5d1855ee216a31f10242676`: `GPUOpenCL` (Adreno 750,
driver 0762.36.1) and `HTP0` (Hexagon v75). OpenCL uses optimized Adreno
kernels, with OpenCL profiling disabled; Hexagon profiling is also disabled.
The benchmark calls the selected backend directly, checks operation support,
and never schedules a CPU fallback.

Weights are `[4096,14336]`, activations are `[14336,batch]` F32, and outputs
are F32. FP16, GGML Q8_0 and Q4_0 describe the **stored weight format**.
Q8_0 is 34 bytes per 32 weights; Q4_0 is 18 bytes per 32 weights.
They are not EXL3, raw INT8/INT4 TOPS, or a guarantee that the two backends
use identical internal arithmetic. For example, batch-1 Q4 has greater error
on the NPU, while several batched GPU paths have greater error than the NPU.
Even the FP16 row is an F16-weight/F32-input backend operation, not an isolated
native FP16 tensor-unit peak measurement.

Before and after every timed run, all matrix outputs must be finite and 64
deterministically distributed outputs must match a CPU FP64 dot product using
the decoded stored weights, with normalized squared error at most `5e-4`.
Copy tests check every output element bit-for-bit twice. A clean process exit,
including backend teardown, is required. Input seed is `0x7ba4139d`.
The largest observed NMSE is `3.0373e-4` (relative RMS error about 1.74%),
on GPU Q4_0 batch 4; the largest sampled absolute error across accepted runs
is 2.837. This is a permissive proxy-benchmark gate, not FP32-equivalent
accuracy or an acceptance test for model translation quality. Actual errors
are published per case so performance is not mistaken for identical precision.

Timing includes graph dispatch and synchronization, not weight preparation,
initialization, validation, or model execution. A graph repeats the operation
approximately 50 ms worth of times, determined by a warmup. The original
upstream performance harness used larger graphs, so these are fresh matched
measurements, not a direct continuation of the previous historical timings.

FP16 batches 1/4/8 and Q8_0 batch 1 run for two seconds; FP16 batch 512 for
one second. Q8_0 batches 4/8/512 and **all Q4_0 cases use 250 ms bursts on
both backends** because longer NPU runs reached the project thermal guard.
Graph boundaries can overshoot the requested duration. These burst values
are not sustained full-load ratings. Q4_0 batch-1 NPU runs span 169.87–185.09
GFLOPS versus GPU 172.85–172.88; the mean does not establish a reliable NPU
advantage at batch 1. FP16 GPU batch-1 runs also span 42.04–50.43 GFLOPS.

GPU FP16 batch 4/8 is unusually slow relative to batch 1. Numerical checks
pass; this is a result for the current backend/shape/kernel selection, not a
claim that the hardware intrinsically slows down with a larger batch.

## Effective bandwidth

Batch-1 packed-weight bytes divided by operation time, decimal GB/s:

| Weight format | GPU | NPU |
|---|---:|---:|
| FP16 | 46.23 | 46.26 |
| Q8_0 | 49.31 | 51.23 |
| Q4_0 | 48.62 | 49.92 |

This is effective model-weight bandwidth, not a physical DRAM bus counter.
Prepacking, backend caches, and internal representations can change actual
traffic. Similar batch-1 performance suggests both paths are bandwidth-bound
for this particular workload; it does not prove a shared cache or Direct Link.

Explicit copy uses a 4096×4096 FP16 tensor (32 MiB), counting 64 MiB read plus
write per operation. Two three-second runs per backend/operation, same ABBA
order, with full bit-exact checks:

| Operation | GPU GB/s | NPU GB/s | GPU ms/op | NPU ms/op |
|---|---:|---:|---:|---:|
| Contiguous copy | 41.12 | 42.50 | 1.632 | 1.579 |
| Transposed copy | 1.198 | 0.516 | 56.03 | 130.12 |

These are backend copy/transpose implementations, not GPU-to-NPU transfers.
All new bandwidth values are decimal GB/s. The historical report's copy
values have been corrected from mislabeled GB/s to GiB/s; its packed-weight
bandwidth values were already decimal and do not change.

## Power protocol and thermal limits

USB was disconnected, wireless ADB was used, and the display remained in
Dozing/Asleep. We read the **current HAL** temperature block, not the stale
cached block in `dumpsys thermalservice`. Signed `ibat_A * vbat_V` estimates
whole-device battery discharge power. Sampling target is 0.5 seconds, including
ADB/query overhead. This is not an accelerator rail measurement; it includes
DRAM, CPU dispatch, radios/ADB, background work, and power conversion losses.
Battery current is quantized and the monitor itself has overhead.

For every format and batch 1/512, both backends run for 30 seconds at **25%
software duty**: each graph is followed by sleep for three times its compute
duration. Reported throughput includes sleep. Power uses samples after the
first five seconds, with a preceding at-least-15-second idle baseline. These
are intermittent-load averages, **not continuous 100%-load power**, and not a
comparison at equal delivered throughput. There is only one sustained run per
condition, in GPU-then-NPU order; confidence intervals are not established.
Do not multiply these rates or watts by four to predict continuous load:
dynamic clock policy and power-state transitions can change with duty.
Per-operation device energy is an approximation using the power sample mean
and whole-run time/op, whose intervals differ slightly. Rates use the sum of
timed `steady_clock` windows, excluding JSON emission between windows.
`CLOCK_BOOTTIME` elapsed exceeds that sum by up to 0.17 seconds (0.56%) in the
30-second runs; logging and possibly brief device suspend contribute to this
gap. JSON also publishes the alternative boottime duration and GFLOPS.

All 12 final 25%-duty runs completed without a thermal stop:

| Weights | Batch | GPU GFLOPS | NPU GFLOPS | GPU battery W | NPU battery W | GPU J/op | NPU J/op |
|---|---:|---:|---:|---:|---:|---:|---:|
| FP16 | 1 | 9.32 | 13.91 | 1.210 | 2.146 | 0.0152 | 0.0181 |
| FP16 | 512 | 129.10 | 951.08 | 1.564 | 4.587 | 0.7285 | 0.2900 |
| Q8_0 | 1 | 13.05 | 25.26 | 1.816 | 2.387 | 0.0163 | 0.0111 |
| Q8_0 | 512 | 249.08 | 1710.08 | 2.279 | 3.378 | 0.5501 | 0.1188 |
| Q4_0 | 1 | 31.27 | 44.96 | 1.127 | 3.116 | 0.0042 | 0.0081 |
| Q4_0 | 512 | 239.87 | 1798.96 | 4.838 | 3.865 | 1.2128 | 0.1292 |

Idle estimates preceding these cases span 0.484–0.802 W. Baseline-subtracted
values are in the JSON but still are not accelerator-only watts. GPU Q4_0
batch 512 consumes more whole-device power than NPU despite lower throughput
in this particular implementation. For batch 1, GPU uses fewer watts in all
three formats, but device energy per completed operation favors GPU only for
FP16/Q4_0 and favors NPU for Q8_0. These observations do not generalize to EXL3.

Maximum active-sample NSP temperature is 73.5°C, GPU 48.9°C, and skin 34.04°C.
Last-five versus first-five timing-window throughput changes range from
-10.1% to +5.8% for GPU and -2.0% to +0.6% for NPU. The GPU Q4_0 batch-1
decline is not proof of thermal throttling: clocks/power policy were not
instrumented, and the GPU sensor peaked at only 43.4°C in that case.

The backend power policies are not identical: Hexagon requests maximum core,
bus and HMX performance, while OpenCL follows the stock dynamic GPU policy.
No clocks, voltage, Android thermal policy, root access, or firmware were
modified. These results compare usable software defaults, not equal-clock
silicon efficiency.

Initial full-duty trials were stopped by the thermal monitor and excluded:

- A Q8_0 batch-512 NPU smoke test observed an instantaneous whole-device
  battery estimate of 16.07 W and maximum NSP sensor 93.9°C before stopping.
  The initial 85°C guard and one-second sampling were too slow for the rise.
- The protocol was tightened to a project stop threshold of 80°C for GPU/NSP,
  85°C for CPU, 42°C skin, 40°C battery, or Android thermal status moderate.
  Sampling was increased to twice per second.
- Full-duty Q8_0 batch 4 and Q4_0 batch 1 also triggered stops. Q4_0 batch 1
  reached 81.3°C around 1.35 seconds. A 50%-duty Q8_0 batch-512 pilot passed
  five seconds but reached 78.2°C, motivating 25% duty for all long runs.

These are polling guards, not hard temperature limit guarantees; brief
overshoot can occur. Aborted timings are retained in raw logs but never mixed
into accepted averages. No NPU-only energy counter or rail measurement is
available on the stock device, as documented in the
[original visibility investigation](2026-10-09-xiaomi-14-ultra.md).

## Reproduction and audit

The isolated harness is [accelerator_bench.cpp](../../tools/accelerator_bench.cpp),
built with NDK r29 / Android API 34 / C++17, `-O3 -Wall -Wextra -Wpedantic
-Werror`, using the Snapdragon toolchain image `arm64-android:v0.7`. It links
the existing baseline package, without modifying upstream source or replacing
model runtime libraries. SDK/Tools are 6.6 / 19.0.07.

```powershell
./tools/build_accelerator_bench.ps1 -Serial <adb-target> -Push
python tools/run_accelerator_bench.py --serial <adb-target> --stage short
python tools/run_accelerator_bench.py --serial <adb-target> --stage sustained
python tools/run_accelerator_bench.py --serial <adb-target> --stage copy
python tools/analyze_accelerator_bench.py <run-directory> --output <summary.json>
python -m unittest discover -s tests -p test_accelerator_bench.py
```

The analyzer checks operation shape, stored-weight byte counts, FLOP/traffic
accounting, window sums, wall/active rates, validation ordering and gates,
requested duration, clean exit, raw-log SHA256, and sustained power against
the recorded unplugged/screen-off telemetry. `--index-range START:END` selects
an exclusive case-index range, one per input directory, for resumed stages.
Machine-readable accepted cases contain log hashes, repeats and rate ranges;
private raw telemetry/device identifiers remain in ignored `benchmark-raw/`.

The [audited summary](2026-10-10-gpu-npu-summary.json) contains 68 accepted
cases: 48 short matrix runs, 12 intermittent power runs, and 8 copy runs.
For the resumed short stage, selection is cases `[0,20)` from
`accelerator-20261010-191409-short`, `[20,32)` from
`accelerator-20261010-192100-short`, and `[32,48)` from
`accelerator-20261010-192519-short`. This preserves two runs per backend per
shape, without mixing failed full-duty trials or earlier superseded durations.
Power and copy datasets are `accelerator-20261010-192711-sustained` and
`accelerator-20261010-193637-copy`, respectively.

## Implication for EXL3 work

For batch-1 proxy kernels, GPU and NPU are close. For large batches, the
current NPU backend is several times faster. Neither result measures GPU
EXL3 dequantization followed by NPU FP16 matrix multiplication, and neither
demonstrates an end-to-end translation speedup. The inference plan still
keeps final FP16 matrix work on the NPU; this benchmark alone does not justify
moving inference to the GPU or claim that the 15 tokens/s goal is met.
