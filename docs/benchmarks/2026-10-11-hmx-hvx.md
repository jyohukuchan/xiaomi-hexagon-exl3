# HMX and HVX matrix performance

For the tested Homura GGUF matrices, the existing FP16 HMX route is clearly
faster than forced HVX at the tested batches 16, 64, 128 and 512. Small-batch gains are not consistent.
These measurements compare complete matrix-kernel routes, including their format
handling, **not native integer HMX against HVX or full-model generation speed**.

## Conditions

- Xiaomi 14 Ultra, Snapdragon 8 Gen 3, v75, stock non-root Android; USB unplugged,
  screen off, no concurrent model or probe process.
- Unmodified llama.cpp `a11f57ba93797579a5d1855ee216a31f10242676`, with runtime
  library hashes bound to the separate kernel-profile evidence.
- Actual Homura Q8_0 and Q4_K tensors: attention gate N=2048,K=2048 and FFN gate
  N=6144,K=2048. Q4_K_M's Q6_K tensors are outside this comparison.
- Each route pair receives the same model artifact and deterministic F32 input.
  Numerical output is checked against CPU double-precision calculations from
  decoded GGUF weights. Every output is finite/written, padded outputs are zero,
  and a 4 KiB output guard must remain intact.
- HMX route: `GGML_HEXAGON_NHMX=1`, `GGML_HEXAGON_MM_SELECT=2`. Input row counts
  are rounded up to 32, including logical batches 1, 4 and 16. Padding work is
  included in the measured time.
- HVX route: `GGML_HEXAGON_NHMX=0`, `GGML_HEXAGON_MM_SELECT=1`, with exactly the
  logical batch's row count. The backend reports HMX disabled in this session.
- Direct HTP0 graph execution with no CPU scheduler fallback. HMX dequantizes
  weights for FP16 matrix work; HVX uses the existing quantized byte-dot route.
  This compares practical routes, not equal-precision arithmetic units in isolation.

The pinned backend normally permits HMX only for more than four input rows.
Merely enabling HMX for batch 1 would therefore measure an auto-selected HVX
kernel. Explicit padding avoids that mistake without modifying the baseline.

## Timing and route verification

Separate profiled processes at logical batches 1 and 64 verify `hmx-tiled` and
`hvx-tiled` for both precisions and shapes. Profile timings are never included in
the performance comparison. The profiling and timing runs use the same client
binary and backend library hashes.

Each measured case first runs one untimed graph computation, then times repeated
graph compute plus host dispatch/synchronization. Tensor loading/upload,
reference calculation and output download are excluded. Runtime profiling is off.
Each format and batch has two trials per route, ordered HMX, HVX, HVX, HMX, with
at least five seconds of cooldown and fresh telemetry before each process.

The 2048×2048 shape uses 50 calls per timed trial. The 6144×2048 shape uses five
calls per trial under the revised short-burst protocol described below. Ratios
are computed from the two routes' mean per-call times, with paired-trial ranges
available in the [audited summary](2026-10-11-hmx-hvx-summary.json).

## Attention gate results

Weights N=2048,K=2048. HMX speedup means HVX time divided by HMX time; less than
one means HMX is slower. All timings are microseconds per matrix call.

| Batch | Q8_0 HMX | Q8_0 HVX | Q8_0 speedup | Q4_K HMX | Q4_K HVX | Q4_K speedup |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 503.14 | 383.59 | 0.76x | 482.94 | 496.54 | 1.03x |
| 4 | 456.74 | 402.00 | 0.88x | 564.31 | 496.49 | 0.88x |
| 16 | 493.53 | 832.73 | 1.69x | 409.00 | 1047.33 | 2.56x |
| 64 | 433.03 | 2122.89 | 4.90x | 499.25 | 2871.09 | 5.75x |
| 128 | 526.41 | 3882.65 | 7.38x | 530.38 | 5172.14 | 9.75x |
| 512 | 972.68 | 13334.43 | 13.71x | 1028.67 | 18062.89 | 17.56x |

Batch-1 Q4_K's 3% mean advantage is marginal. Q8_0 batch 4 varies from 0.65x to
1.12x between paired trials. These do not establish a reliable small-batch win or
a universal batch threshold. At batch 16 both formats are faster in each trial.

## Thermal protocol and limits

The first 6144×2048, Q8_0, HVX batch-512 trial with 50 consecutive timed calls
crossed the project's 80 C NPU stop threshold: the sampled `nsp1` reached 81.7 C.
The guard sent SIGINT, the client rejected the interrupted trial, and the process
exited. Android thermal status was still 0; 80 C is the project's conservative
stop rule, **not a measured system throttling threshold**. The raw failed dataset
is retained locally and excluded from accepted timings.

After cooldown, the entire larger-shape comparison is repeated with five calls
per trial for **both** routes and all batches. Stop thresholds are unchanged.
This short-burst result is not a sustained-performance rating. Lower call counts
also increase sensitivity to dispatch and scheduling noise, so paired ranges must
be considered before interpreting small differences.

Only whole-device battery telemetry is accessible here. These short and unequal
compute windows do not support an HMX/HVX power-efficiency ranking; telemetry is
used for charging, screen-state and temperature safety checks.

Accepted runs reached sampled NPU maxima of 74.7 C for the smaller shape and
71.6 C for the larger shape. All 96 timed cases and 16 separate route-profile
cases passed their correctness and phone-state checks.

## Implications

Existing HMX acceleration already gives substantial gains over HVX for larger
batches with GGUF weights, even though its matrix arithmetic is FP16. Native
integer HMX would have to beat this optimized route, not just forced HVX.
An integer-kernel capacity number is therefore not sufficient to justify replacing
the existing implementation.

Batch here means the number of activation rows in a Linear matrix operation.
It may arise from prompt tokens or simultaneous decode sequences; it is not
automatically the number of API requests. Attention, recurrent state, scheduling
and other operators prevent translating these ratios directly into tokens/s.

The [existing integer-engine survey](../validation/hexagon-integer-engines.md)
identifies QNN-based W8A8 and LPBQ alternatives. The original EXL3 runtime,
model storage and FP16 KV policy remain unchanged.

## Reproduction

Build and deploy the independent client with
`tools/build_int_hmx_micro_probe.ps1 -Push -Serial SERIAL`. The original inference
libraries are not overwritten. Use a pinned read-only llama.cpp baseline checkout.

```text
python tools/run_hmx_hvx_compare.py --serial SERIAL --phase profiles --batches 1 64 --trials 1
python tools/run_hmx_hvx_compare.py --serial SERIAL --phase timings
python tools/run_hmx_hvx_compare.py --serial SERIAL --phase profiles --n 6144 --k 2048 --tensor blk.0.ffn_gate.weight --batches 1 64 --trials 1
python tools/run_hmx_hvx_compare.py --serial SERIAL --phase timings --n 6144 --k 2048 --tensor blk.0.ffn_gate.weight --calls 5
```

`tools/analyze_hmx_hvx_compare.py` audits raw hashes, lifecycle, numerical gates,
padding, route profiles, call counts, pair coverage, matched artifacts and safe
phone state before producing the public summary. It rejects profiled timings and
partial or thermally interrupted comparisons. Raw logs and model files remain
ignored local artifacts; the summary preserves their hashes and source provenance.

The Android client builds with warnings as errors. All 74 portable Python tests
pass, including the new route-comparison tests and rejection of profiled timings.
The unrelated CUDA-refit test requires a host `torch` installation and is excluded
from this portable test set; no CUDA verification is claimed.
